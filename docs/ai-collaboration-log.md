# 我和 AI 一起造了这个工具——一份诚实的协作日志

> 面试官您好。这个项目 95% 的代码由 AI(Claude Code / ZCode 里的 GLM)编写,但**每一个决定、每一次验收、每一个坑的定位都是我做的**。这篇日志讲清楚:分工是什么、我怎么判断 AI 对不对、以及为什么这种协作方式本身就是作品的一部分。

## 一、分工:我是需求方和验收方,AI 是工程团队

| 环节 | 我做的 | AI 做的 |
|---|---|---|
| 需求 | 定义"监控+告警+资金建议"的真实场景,砍出 MVP | — |
| 架构 | 决定零依赖、本地 JSON 存储、模块边界 | 给出实现方案供我选择 |
| 开发 | 提结构化指令(背景+任务+要求+格式),逐模块验收 | 写了几乎全部代码 |
| 安全审计 | 要求"带 file:line 证据、只报高置信" | 用 Trail of Bits 方法论审出 4 项发现 |
| 修复验证 | 拒绝"改了就好",要求回归测试锁定 | 写了 14 个 node:test 用例 |
| 发布 | 决定开源时机、README 结构、博客角度 | 生成文档初稿,我逐句改 |

## 二、三个"判断 AI 对不对"的实战故事

### 故事 1:它显示成功了,但日志说它在撒谎

给 Codex 接 GLM 模型时,终端连续几次返回 `GLM online`,看起来大功告成。但我加的本地代理桥有请求日志——**日志里 60 次失败、0 次来自 Codex 的成功**。那些"成功"其实是后台进程把配置改回了旧模型,答话的根本不是 GLM。

**教训:验收 AI 的产出,不看它的输出像不像对的,看证据链。** 我后来把"查桥日志"变成了固定验收动作,并写进了体检脚本。

### 故事 2:400 错误,二分法找到"无名工具"

桥接通后,上游持续返回 400(参数错误)。我没有让 AI 猜原因,而是:①给桥加**请求转储**,拿到真实载荷;②设计**二分矩阵**——去掉工具✓、单个工具逐个试——最终定位到 Codex 会发送一个没有 name 的内置工具,格式转换后变成"无名 function"被上游拒绝。

**教训:AI 擅长给出看起来合理的解释,但定位 bug 要靠可复现的实验设计。**

### 故事 3:安全审计,我要求"证据否则闭嘴"

AI 审计自己的代码容易报喜。我给它的硬约束是:**每条发现必须带 file:line 和代码片段,只详报高置信项**。最终 4 项发现(重定向无限制、外部数据直入决策链、ANSI 注入、JSON 损坏静默清零)全部有据可查,修复后 14 用例回归全绿。

**教训:prompt 里写清楚"什么是合格的产出",AI 的输出质量会上一个台阶。**

## 三、AI 帮我省了什么,没省什么

- **省了**:语法记忆、API 文档查阅、样板代码、初稿生成——大概 80% 的打字量
- **没省**:需求判断(做不做、做到哪)、方案取舍、异常情况下的-debug-方向感、以及**验收责任**——线上跑错了,锅是人的,不是 AI 的

## 四、给面试官的三分钟讲法

1. **我做了什么**:定义需求 → 指挥 AI 开发 → 强制安全审计 → 测试锁定 → 开源发布,端到端一人闭环
2. **我怎么用 AI 的**:结构化指令 + 分模块验收 + 证据要求,把 AI 当工程团队管理,不是当搜索引擎
3. **踩了什么坑**:假成功(用日志识破)、无名工具(用转储+二分定位)、AI 自审自报喜(用证据门槛约束)
4. **沉淀了什么**:这套协作方法本身写成了开源 skill(ai-first-delivery),流程可复制
